# Research & Technical Decisions: Shared System-Level Neovim Configuration

**Branch**: `017-share-neovim-config` | **Date**: 2026-10-17 | **Spec**: [spec.md](spec.md)

---

## Decision 1: System-Level Neovim Engine via NixOS `programs.neovim`

### Decision
Configure Neovim using the native NixOS `programs.neovim` module inside `modules/core/neovim.nix` (`flake.modules.core.neovim.nixos`):

```nix
programs.neovim = {
  enable = true;
  defaultEditor = true;
  viAlias = true;
  vimAlias = true;
  withNodeJs = true;
  withPython3 = true;
};
```

Remove the standalone `vim` package from `environment.systemPackages` in `modules/core/base.nix`.

### Rationale
- **No Home Manager Requirement**: `homelab` explicitly disables Home Manager (`enableHomeManager = false` in `modules/hosts/homelab.nix`). NixOS's built-in `programs.neovim` module supports the exact same options (`enable`, `defaultEditor`, `viAlias`, `vimAlias`, `withNodeJs`, `withPython3`) at the system level.
- **Avoids Binary Collisions**: When `programs.neovim.vimAlias = true` is set in NixOS, the wrapped Neovim derivation exposes `/run/current-system/sw/bin/vim`. Removing standalone `pkgs.vim` from `modules/core/base.nix` avoids duplicate `bin/vim` collisions in `system-path` and ensures `vim` and `vi` consistently launch Neovim across all hosts using `core.neovim`.

### Alternatives Considered
- **Enabling Home Manager on `homelab`**: Rejected because the user explicitly requested sharing the Neovim configuration on `homelab` *without* resorting to Home Manager.
- **Maintaining two separate Neovim modules (one NixOS, one Home Manager)**: Rejected because it violates DRY and SC-001; a single NixOS-level `core.neovim` module works identically on both `desktop-pc` and `homelab`.

## Decision 2: Declarative `~/.config/nvim` Symlink via `systemd.tmpfiles.rules`

### Decision
Replace Home Manager's `xdg.configFile."nvim".source = ./dotfiles/nvim;` with NixOS `systemd.tmpfiles.rules` in `modules/core/neovim.nix`:

```nix
systemd.tmpfiles.rules = [
  "d /home/${vars.userName}/.config 0755 ${vars.userName} users -"
  "L+ /home/${vars.userName}/.config/nvim - - - - ${./dotfiles/nvim}"
];
```

### Rationale
- **Atomic Store Path Updates (`L+`)**: Unlike `L` (which only creates a symlink if the target path does not exist), `L+` recreates the symlink whenever the target store path (`${./dotfiles/nvim}`) changes across NixOS generations during `nixos-rebuild switch` / `nh os switch` or boot.
- **Guaranteed Parent Directory (`d`)**: Ensuring `/home/${vars.userName}/.config` exists with `0755 ${vars.userName} users` matches the directory ownership generated by `preservation` on `homelab` and prevents symlink creation failures on fresh systems.
- **Read-Only Store Compatibility**: The existing `lua/config/lazy.lua` already configures `lockfile = vim.fn.stdpath("data") .. "/lazy-lock.json"`, so `lazy.nvim` never attempts to write to the read-only `/nix/store` target of `/home/${vars.userName}/.config/nvim`.

### Alternatives Considered
- **Setting `$XDG_CONFIG_DIRS` or wrapping `nvim` with `-u`**: Rejected because standard LazyVim expects `vim.fn.stdpath("config")` (`~/.config/nvim`) to contain `init.lua` and `lua/` so `require("config.lazy")` and `{ import = "plugins" }` resolve naturally.
- **Activation script (`system.activationScripts`) with `ln -sfn`**: Rejected because `systemd.tmpfiles.rules` is the idiomatic, declarative NixOS mechanism for managing filesystem entries and symlinks.

## Decision 3: Module Boundary & Dotfiles Colocation (`core.neovim` vs `desktop.editors`)

### Decision
1. Create `modules/core/neovim.nix` defining `flake.modules.core.neovim.nixos` and move `modules/desktop/dotfiles/nvim/` to `modules/core/dotfiles/nvim/`.
2. Provision all cross-platform CLI dependencies required by LazyVim (`git`, `gcc`, `gnumake`, `ripgrep`, `fd`, `tree-sitter`, `curl`, `unzip`, `gnutar`, `gzip`) in `environment.systemPackages` inside `modules/core/neovim.nix`.
3. Keep `wl-clipboard`, `programs.vscode`, and `programs.zed-editor` in `modules/desktop/editors.nix` (under `homeManager`).
4. Add `core.neovim` to `features` in both `modules/hosts/desktop-pc.nix` and `modules/hosts/homelab.nix`.

### Rationale
- **Dendritic Colocation**: Colocating `modules/core/neovim.nix` with `modules/core/dotfiles/nvim/` keeps the core domain self-contained without cross-domain relative paths (`../desktop/dotfiles/nvim`).
- **Headless Server Hygiene**: Keeping `wl-clipboard`, VS Code, and Zed in `modules/desktop/editors.nix` ensures `homelab` only installs headless CLI dependencies required by LazyVim.

### Alternatives Considered
- **Keeping `dotfiles/nvim` inside `modules/desktop/dotfiles/nvim` and referencing `../desktop/dotfiles/nvim` from `modules/core/neovim.nix`**: Rejected because a `core` module should not depend on assets inside the `desktop` domain.

## Decision 4: Impermanence State Persistence on `homelab` (`core.preservation`)

### Decision
Update `modules/core/preservation.nix` under `preservation.preserveAt."/persistent".users.${vars.userName}.directories` to persist:
- `.local/share/nvim` (LazyVim cloned plugins, `lazy-lock.json`, and compiled Tree-sitter parsers)
- `.local/state/nvim` (undo history, ShaDa registers, and editor session state)

Replace the commented-out `# ".local/state/neovim"` placeholder with these two active entries.

### Rationale
- **Avoids Re-Cloning & Recompiling on Boot**: `homelab` wipes its root tmpfs on every reboot. Persisting `.local/share/nvim` ensures `lazy.nvim` and all LazyVim plugins remain installed across reboots without network fetches or C compilation of Tree-sitter grammars.
- **Preserves Editing History**: Persisting `.local/state/nvim` retains ShaDa marks, command history, and persistent undo trees across reboots.
- **Correct Directory Name**: Neovim uses `$XDG_DATA_HOME/nvim` (`.local/share/nvim`) and `$XDG_STATE_HOME/nvim` (`.local/state/nvim`), not `neovim`.
